# 消费者体验问题订单分析

> 把体验问题订单从「客服的锅」还原成「哪个环节造成的」。

## 它解决什么

平台后台导出的体验问题表，通常长这样：

| 问题类型 | 问题详情 | 问题部门 |
|---|---|---|
| 消费者求助平台 | 售后-退款问题 | 客服部 |
| 客服服务差 | 旺旺差评 | 客服部 |

直接拿这张表汇报，结论必然是「客服要加强培训」——而真实原因可能是某个批次的摄像头主板坏了。

**这个 skill 干一件事：把「谁在处理」还原成「谁造成的」。**

## 核心方法：三段式

```
归因 → 定位 → 闭环
```

### 一、归因：按消费者旅程六阶段，不按平台枚举

| 阶段 | 含义 | 根因责任归属 |
|---|---|---|
| S1 售前呈现 | 描述不符、夸大宣传、规格标错 | 运营部 |
| S2 下单支付 | 价格争议、优惠未兑现、超卖 | 运营部 |
| S3 履约发货 | 延迟发货、虚假发货、漏发错发 | 仓储部门 |
| S4 物流配送 | 派送停滞、丢件、破损 | 仓储 / 承运商 |
| S5 收货体验 | 质量问题、故障、做工 | 采购部 / 供应商 |
| S6 售后维权 | 退款难、客服态度、差评 | 客服部（仅受理） |

匹配顺序即优先级，S1 → S6 依次命中即停。所以「质量问题引发的退款」判给 S5 而不是 S6，天然实现**上游优先**。

平台的枚举分类会随类目变，消费者旅程不会。这是这套归因能跨品类复用的原因。

### 二、定位：SKU 规格 × 时间批次

- **规格归因**：把问题摊到规格属性上，区分「全系通病」还是「某个规格独有」
- **爆发节奏**：付款到首次问题发生的天数分布
  - 中位 ≤ 3 天 → 收货前后就炸，属商品/发货端，**客服拦截无效**
  - 单周占比 ≥ 40% → 批次性，查该批次来货与活动波次
  - 均匀分布 → 结构性缺陷，靠单次整改解决不了

### 三、闭环：责任穿透 + 可验收指标

- **受理部门 ≠ 根因部门**：平台字段里的「问题部门」记录的是谁在处理，不是谁造成
- 每条整改动作都带：责任部门 + 具体动作 + 验收指标

## 快速开始

```bash
python scripts/analyze.py --input 订单表.csv --output metrics.json
python scripts/build_report.py --metrics metrics.json --output 报告.html
```

输入支持 `.csv` / `.json` / `.xlsx`，**零第三方依赖**（纯标准库，xlsx 用 zipfile + ElementTree 解析）。

表头自动映射，「订单金额(元)」「实付金额」「支付金额」都认，兼容淘宝、天猫、京东、拼多多、抖音的导出格式差异。

常用参数：

- `--sku-keys 内存容量,颜色分类` 指定要拆解的规格属性
- `--rules rules.json` 用自定义归因规则（类目不同，关键词不同）
- `--top 15` 调整 Top N

## 输出报告的七个章节

1. 问题发生在消费者旅程的哪个环节
2. **责任穿透：受理部门 ≠ 根因部门**
3. 问题详情 · 二级归因拆解
4. SKU 规格归因 · 问题落在哪些属性上
5. 爆发节奏 · 付款到问题发生用了多久
6. 问题订单明细（含归因命中词与置信度）
7. 改进动作建议 · 含责任部门与验收指标

## 置信度机制

不是所有问题都能从字段里判断根因。一句「售后-退款问题」可能来自质量、发货或描述不符，只是最后都走到了退款。

| 置信度 | 判定 | 处理 |
|---|---|---|
| high | 命中具体词（质量、延迟发货、派送停滞） | 可直接作结论 |
| low | 只命中宽泛词（退款、售后、投诉） | **必须人工回溯工单** |
| none | 无任何命中 | 归入 S0，补录后重跑 |

报告会单独统计低置信条数并标红。**这是故意留的不确定性——宁可少下结论，不可把推断当事实。**

## 五条铁律

1. 不许把「受理部门」当「根因部门」汇报——这是本项目存在的全部理由
2. 低置信项不许当确定结论写
3. 口径不明不算率（分母说不清就只报绝对值和占比）
4. 样本太小时说清局限（单品 < 20 条只作线索）
5. 每个整改动作必须能验收（写不出指标的行动不写进报告）

## 安装

把整个文件夹放到你的 skills 目录：

- Windows：`C:\Users\你的用户名\.workbuddy\skills\`
- macOS / Linux：`~/.workbuddy/skills/`

重新开一个对话，说「分析体验问题订单」即可自动调用。

## 口径说明

默认六阶段（S1 售前 → S6 售后）是通用口径。若沿用「生命周期五段」，用 `--rules assets/rules_lifecycle5.json` 切换。**两套结论不可混用。**

## 局限

- 归因基于关键词规则，是**推断**不是事实，低置信项须人工复核后使用
- 只分析你提供的导出数据，不含任何平台实时查询能力
- 示例数据因包含真实业务订单信息，未随仓库发布；用你自己的订单表即可直接跑
