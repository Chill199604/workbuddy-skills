# 消费者体验问题订单分析

## 这个技能解决什么

平台后台给你的体验问题表，通常长这样：问题类型「售后-退款问题」、问题部门「客服部」。
直接拿这个表汇报，得出的结论一定是「客服要加强培训」——而真实原因可能是某个批次的摄像头主板坏了。

**本技能的核心价值：把「谁在处理」还原成「谁造成的」。**

## 何时用

- 手里有一份平台导出的体验问题 / 差评 / 投诉 / 纠纷订单表，要出分析报告
- 要向管理层汇报「体验分为什么掉」「差评为什么涨」并给出整改动作
- 要划责任部门、定整改优先级、写质检问题描述
- 面试作品集：需要一份能体现管理视角（而非执行视角）的分析案例

**不适用**：纯退货率统计（走 `ecommerce-return-rate`）、退货损失与利润修复（走 `ecommerce-returns-profit-recovery`）。本技能看的是**问题性质与根因**，退货率看的是**比例与趋势**。

## 核心方法：三段式

```
归因（Attribution）  →  定位（Localization）  →  闭环（Closure）
 这个问题属于哪个环节     落在哪个 SKU / 哪个批次     谁整改、改什么、怎么验收
```

### 第一段：归因 —— 按消费者旅程六阶段，不按平台枚举

| 阶段 | 含义 | 根因责任归属 |
|---|---|---|
| S1 售前呈现 | 描述不符、夸大宣传、规格/尺寸标错 | 运营部（商品/详情页） |
| S2 下单支付 | 价格争议、优惠未兑现、超卖 | 运营部（活动/价格） |
| S3 履约发货 | 延迟发货、虚假发货、漏发错发、缺货 | 仓储部门 |
| S4 物流配送 | 派送停滞、丢件、破损、配送异常 | 仓储部门 / 承运商 |
| S5 收货体验 | 质量问题、故障、做工、安装困难 | 采购部 / 供应商（品质） |
| S6 售后维权 | 退款难、运费争议、客服态度、差评 | 客服部（受理） |

**匹配顺序即优先级**：S1 → S6 依次匹配，命中即停。所以「质量问题→申请退款」判给 S5 而不是 S6，天然实现了上游优先。

关键词规则见 `references/taxonomy.md`，可按类目自行扩展。

### 第二段：定位 —— SKU 规格 × 时间批次

- **SKU 规格归因**：把问题摊到规格属性（内存 / 机型 / 颜色）上，区分「全系通病」还是「某个规格独有」
- **爆发节奏**：付款 → 首次问题发生的天数分布
  - 中位 ≤ 3 天 → 收货前后就炸，属商品/发货端，客服拦截无效
  - 集中某一周（占比 ≥ 40%）→ 批次性，查该批次来货与活动波次
  - 均匀分布 → 结构性，靠单次整改解决不了，要改流程

### 第三段：闭环 —— 责任穿透 + 可验收指标

- **受理部门 ≠ 根因部门**：平台字段里的「问题部门」记录的是谁在处理，不是谁造成。报告第 2 章专门做这层穿透
- 每个整改动作都要带：责任部门 + 具体动作 + 验收指标

## 工作流

### 1. 确认输入与口径

问清三件事（用户没说就按默认并注明）：
- 数据时间范围、是否全量
- 「销量」字段的口径（SKU 级累计销量还是区间销量）—— 影响问题率分母，口径不明就**不要算问题率**
- 是否只要某个商品 / 某类问题

### 2. 跑分析

```bash
python scripts/analyze.py --input 订单表.csv --output metrics.json
python scripts/build_report.py --metrics metrics.json --output 体验问题分析报告.html
```

常用参数：
- `--sku-keys 内存容量,颜色分类` 指定要拆解的规格属性（默认自动识别全部）
- `--rules my_rules.json` 用自定义归因规则（类目不同，关键词不同，见 taxonomy.md）
- `--top 15` 调整 Top N

输入支持 `.csv` / `.json` / `.xlsx`，**零第三方依赖**（纯标准库）。表头自动映射，兼容淘宝/天猫/京东/拼多多/抖音的命名差异（如「订单金额(元)」「实付金额」「支付金额」都能认）。

### 3. 必做的人工复核

报告出来后**不要直接交**，先做这两件事：

1. **看低置信条数**。只命中「退款/售后/投诉」等宽泛词的订单会被标为低置信（第 6 章明细表里有「置信」列）。这部分根因在上游，**必须回溯原始聊天/工单**确认，再决定算谁的。
2. **看责任穿透表**。若「客服部」的疑似误挂条数 > 0，说明有上游的锅被挂在客服头上，汇报时要点出来。

### 4. 输出

用 `present_files` 把 HTML 报告给用户。报告为单文件、离线可看、可直接转发。

## 铁律

1. **不许把「受理部门」当「根因部门」汇报。** 这是本技能存在的全部理由。
2. **低置信项不许当确定结论写。** 标出来，写「待回溯」。宁可少下结论，不可虚高。
3. **口径不明不算率。** 分母说不清就只报绝对值和占比，不报问题率。
4. **样本太小时说清局限。** 单品 < 20 条问题单，结论只能作为线索，不能作为整改依据。
5. **每个整改动作必须能验收。** 写不出指标的行动不写进报告。

## 汇报口径（给管理层/面试用）

- 开口先给**结论**：问题集中在哪个环节、根责在谁、影响多少金额
- 再给**证据**：阶段分布、责任穿透、SKU 归因、爆发节奏
- 最后给**动作**：谁改、改什么、验收指标、多久见效
- 主动说**局限**：样本量、低置信项、口径假设

## 文件说明

| 文件 | 用途 |
|---|---|
| `scripts/analyze.py` | 分析引擎：字段映射 → 六阶段归因 → 指标计算 |
| `scripts/build_report.py` | 渲染七章 HTML 报告 |
| `references/taxonomy.md` | 归因关键词字典 + 平台字段别名表（可扩展） |
| `references/playbook.md` | 指标判读阈值、常见误判、汇报话术 |
| `assets/rules_lifecycle5.json` | 备选口径：生命周期五段（付款/发货/运输/签收/使用），`--rules` 调用 |

> 本地另有 `assets/sample_orders.csv`（示例输入）与 `assets/example_report.html`（示例输出），因含真实业务订单信息，已用 `.gitignore` 排除，不随仓库发布。用任意订单表即可直接跑。

> **口径说明**：默认六阶段（S1 售前 → S6 售后）是通用口径。若沿用「生命周期五段」口径，加 `--rules assets/rules_lifecycle5.json` 即可，两套结论不可混用。

## 边界

- 只分析**用户提供的导出数据**，不虚构平台实时查询能力
- 归因基于关键词规则，是**推断**不是事实；结论须人工复核后使用

## 相关技能（同一套电商售后分析体系）

- **refund-order-analysis**（退款单数据分析）：定量·金额·比例·趋势视角——回答「退款总共掏了多少钱、哪个板块/商品最烧钱、趋势怎么走」。本 Skill 是它的**定性互补**：本 Skill 看「这笔退款/投诉是什么性质、根子在谁」，它看「退款花了多少钱、占比多少」。两者在「退款」上是一体两面，合起来就是完整的电商售后/退款分析体系。
- 同体系可补成员（均在 `workbuddy-skills` 仓库以子目录收纳）：退货率分析、客诉分析、评价/VOC 分析、品控归因等。
